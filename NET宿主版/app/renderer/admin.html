文字识别引擎（OCR）

截图后先做文字识别，识别质量直接决定后续辨证/审方准确性。推荐 PP-OCRv6（百度飞桨第六代，中文识别精度较上一代再提升 5.1%，单模型覆盖中英日）。环境缺失时自动回落到系统内置 OCR。
识别引擎
模型档位
Python 路径
仅在使用 PaddleOCR 引擎时需要；指定 OCR 专用 Python 解释器（python.exe）路径。
识别引擎常驻内存：应用启动后自动在后台加载一次模型（启动后即后台预热），之后每次截图识别不再重复加载 —— 单次冷启动的建引擎开销约 3~15 秒（低配机更久）只在首次付一次。首次使用 PP-OCRv6 会自动下载模型（约 35MB，需联网，之后完全离线）；RapidOCR(ONNX) 通道使用内置 ONNX 模型，完全离线、无需下载。
实测（同一张处方图，542×360）：tiny ≈ 1.8 秒 / small ≈ 6.6 秒 / medium ≈ 20 秒，识别内容等价，故默认 tiny。实测（全屏 2752×1104，同一张截图）：PaddleOCR tiny 首次 23.5 秒 → 常驻复用 11.6 秒；RapidOCR 首次 7.3 秒 → 常驻复用 4.1 秒。
低配主机建议：档位固定 tiny（模型 1.5M，内存与 CPU 压力最小），若仍偏慢可把引擎切到「仅 RapidOCR」——它比 PaddleOCR tiny 再快约 2.8 倍，代价是偶有整框漏字（已实测漏「甘草」等），需要时切回 auto 复核。

引擎说明

PP-OCRv6（推荐）：检测精度 +4.6%、识别精度 +5.1%（对 PP-OCRv5_server），对医学术语的形近字、繁体、漏字识别更稳；CPU 提速 5.2×。
RapidOCR（ONNX 通道，可主动选用）：用 onnxruntime 推理 同一套 PP-OCRv6 识别模型（scripts/models 内置，不联网、不下载），内存占用明显更低、任何 x64 CPU 都能跑；本机 CPU 不支持 AVX 时 auto 档会自动切到该通道（paddle 原生核心在无 AVX 的 CPU 上无法加载）。识别精度与原生通道同源，耗时随 CPU 而异。
tesseract.js（离线兜底）：纯 JS 实现，随应用内置中文语言包（vendor/tessdata），无 Python、无网络依赖；「屏幕文字」入口即走此引擎。中文密集文本精度不如 PP-OCRv6，适合快速识字/环境缺失时兜底（auto 档在 PP-OCRv6 与系统 OCR 均失败时自动启用）。
系统内置 OCR：Windows.Media.Ocr，零依赖、启动快，但中文密集文本与医学术语易出错（如 损→伍、滞漏字）。
两级纠错仍在生效：无论用哪个引擎，识别文本都会再过一次术语库纠错（形近字/偏旁脱落/证型库约束）。

点评红线 · 规则设置

设定处方点评的四条判定红线：超过提醒值按一般问题提示（warn），超过红线值直接判不合理（error）。各机构口径不同，可按本院规定调整；取消勾选即停用该类红线。配置存本机 data.db（kv['rxrule']），Electron 版与 .NET 版共用同一份。
红线类别启用提醒值红线值说明
① 味数红线 味 味 单张处方药味数。门诊饮片处方一般宜 ≤20 味，≥28 味从严。红线值不得小于提醒值（自动纠正）。
② 单日剂量红线 g/日 g/日 单味药单日剂量＝每剂剂量 × 每日剂数（用法「每日N剂」折算）。外用方豁免，不按内服量核查；非重量单位（ml/粒/丸）不计量。
③ 天数红线 剂 剂 处方开具剂数（按「N味M剂」或裸数识别）。《处方管理办法》：一般不超过 7 日用量，急诊 3 日；慢性病可适当延长但应注明理由。
④ 辨证红线 % % 方-证相符率下限＝有支撑证据（病域/证型/症状）的药味占比。低于提醒值提示、低于红线值判不合理。率越低越严重，红线值不得高于提醒值。
